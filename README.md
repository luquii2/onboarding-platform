## Backend

### Необходимый инструментарий

Требуется Python 3.14+ и PostgreSQL 13+.

### Подготовка базы данных

Подключиться к PostgreSQL под пользователем `postgres` (через DBeaver, pgAdmin или psql) и выполнить:

```sql
CREATE USER onboarding_app_admin WITH PASSWORD 'TST5399112';
CREATE DATABASE onboarding_db OWNER onboarding_app_admin;
```

### Установка библиотек и запуск

```bash
cd backend
python -m venv venv
venv\Scripts\activate           # Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env          # Linux/macOS: cp .env.example .env
alembic upgrade head            # создать или обновить таблицы в базе
uvicorn main:app --reload
```

Проверка работы (GET-запрос, возвращает JSON ответ, если база недоступна - ошибка 500): http://127.0.0.1:8000/testconnect/
Документация API: http://127.0.0.1:8000/docs

   Все эндпоинты API начинаются с `/api/v1`. Поля в JSON — в стиле camelCase.
   Пока часть эндпоинтов — заглушки: данные проверяются, но возвращаются примеры.

После копирования впишисать в `backend/.env` секретный ключ для подписи токенов (`SECRET_KEY`). Сгенерировать:

    python -c "import secrets; print(secrets.token_urlsafe(64))"

### Применение миграций

После изменения моделей в `backend/models`:

```bash
alembic revision --autogenerate -m "краткое описание изменений"
alembic upgrade head
```

Перед применением проверьте сгенерированный файл в `migrations/versions`.
После `git pull` выполните `alembic upgrade head`, чтобы получить изменения базы от других участников.

### Авторизация

Вход по JWT. `POST /api/v1/auth/register` и `POST /api/v1/auth/login` возвращают `accessToken`; в запросах панели его нужно передавать в заголовке `Authorization: Bearer <accessToken>`. Токен действует сутки (`ACCESS_TOKEN_EXPIRE_MINUTES`).

- Пароли хранятся только в виде хэша Argon2.
- E-mail приводится к нижнему регистру.
- При ошибке входа ответ одинаковый для неверного e-mail и неверного пароля.
- `POST /api/v1/auth/logout-all` отзывает все токены пользователя (поле `users.token_version`).
- Открыты без токена: `/api/v1/auth/register`, `/api/v1/auth/login`, `/api/v1/public/...`.

Формат ошибок: `{"detail": {"code": "...", "message": "..."}}`.

| Код | `code` | Когда |
| --- | --- | --- |
| 409 | `EMAIL_ALREADY_EXISTS` | E-mail уже зарегистрирован |
| 401 | `INVALID_CREDENTIALS` | Неверный e-mail или пароль |
| 401 | `NOT_AUTHENTICATED` | Нет токена |
| 401 | `INVALID_TOKEN` | Токен поддельный, истёк или отозван |
| 409 | `SITE_ALREADY_EXISTS` | Сайт с таким адресом уже есть у пользователя |
| 404 | `SITE_NOT_FOUND` | Сайт не существует или принадлежит другому пользователю |
| 409 | `REVISION_CONFLICT` | Черновик изменён в другой вкладке (в ответе `currentRevision`) |
| 422 | `PAGE_OUTSIDE_SITE` | Страница проекта не относится к сайту |
| 413 | `PROJECT_TOO_LARGE` | Проект больше 500 КБ |
| 422 | `PUBLISH_NOT_READY` | Сценарии не готовы к публикации (в ответе список `errors`) |
| 404 | `NOT_PUBLISHED` | У сайта ещё нет публикаций |
| 404 | `VERSION_NOT_FOUND` | Запрошенной версии публикации нет |

### Сайты

- Адрес сайта проверяется и нормализуется на сервере: только `http`/`https`, без логина и пароля, без `?` и `#`; домен в нижнем регистре, без стандартного порта, кириллические домены — в punycode. Из адреса получаются `origin` и `basePath` (папка сайта).
- При добавлении сайта в одной транзакции создаются тема оформления и черновик с одним пустым сценарием.
- Все эндпоинты с `{site_id}` получают сайт через зависимость `OwnedSite` (`api/deps.py`): чужой и несуществующий сайт дают одинаковый ответ 404.
- Удаление сайта удаляет его тему, черновик, публикации и события.

### Черновики и публикация

- Черновик сохраняется одной командой `UPDATE … WHERE revision = baseRevision RETURNING …`: из двух одновременных сохранений от одной ревизии проходит одно, второе получает 409.
- Все страницы проекта должны быть внутри сайта: тот же `origin` и путь внутри `basePath`.
- Публикация блокирует строки сайта и черновика (`SELECT … FOR UPDATE`), поэтому одновременные нажатия не создают лишних версий. Повторная публикация той же ревизии возвращает существующую версию.
- Перед публикацией проверяются те же условия, что в панели (`services/publishing.py` повторяет `triggerKey`, `triggerErrors`, `isDraft`, `exportProject` из `src/model.js`).
- Публикация — неизменяемый снимок включённых сценариев с номером версии. Тема оформления добавляется к конфигурации при выдаче, поэтому её изменения не требуют повторной публикации.

### Настройки

Обязательная настройка в `backend/.env` — `DATABASE_URL`. Остальные необязательные (значения по умолчанию подходят для локальной разработки):

| Настройка | Что задаёт |
| --- | --- |
| `CORS_ORIGINS` | Адреса панели, которым разрешён доступ к API, JSON-список: `["http://localhost:5173"]` |
| `PUBLIC_API_URL` | Адрес бэкенда для ссылок в коде подключения виджета |
| `WIDGET_URL` | Адрес файла виджета |
| `EDITOR_ORIGIN` | Адрес панели для атрибута `data-editor-origin` |
| `SECRET_KEY` | Обязательно. Секретный ключ для подписи токенов, минимум 32 символа |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Срок действия токена в минутах, по умолчанию 1440 (сутки) |
| `WIDGET_ACTIVE_HOURS` | Сколько часов после последнего сигнала виджет считается работающим, по умолчанию 24 |

Для эндпоинтов-заглушек PostgreSQL не нужен, но файл `backend/.env` должен существовать.

### Модель данных

| Таблица | Что хранит |
| --- | --- |
| `users` | Аккаунт компании: название, e-mail, хэш пароля, время согласия с условиями использования |
| `sites` | Сайты пользователя: базовый адрес (`base_url`, `origin`, `base_path`), данные сигнала подключения виджета, номер текущей публикации |
| `themes` | Настройки с экрана «Настройка вида»: цвета, шрифт, скругление, положение по умолчанию. Одна тема на сайт |
| `project_drafts` | Проект сайта целиком в JSONB (формат `schema: 4` из `src/model.js`) с номером ревизии |
| `publications` | Неизменяемые снимки опубликованных сценариев с номерами версий — их получает виджет |
| `events` | События виджета с версией конфигурации, временем события и временем получения сервером |

Основные решения:

- **Сценарии и шаги хранятся внутри JSON** черновика и публикаций, отдельных таблиц для них нет. Панель сохраняет проект целиком, поэтому на сервере он хранится в том же виде.
- **Ревизия черновика** увеличивается при каждом сохранении. Если проект изменили в другой вкладке, сохранение устаревшей версии отклоняется, и свежие изменения не теряются.
- **Публикации не изменяются** после создания. Посетитель, начавший тур, проходит его до конца по той версии, с которой начал, даже если вышла новая публикация.
- **Id сценариев и шагов** создаёт панель, сервер их не меняет. Уникальность проверяется в пределах сайта, а не глобально. Id сайта генерирует сервер (случайный UUID).
- **События уникальны по паре** `(site_id, event_id)`: повторная отправка того же события не искажает статистику.
- **Каскадное удаление:** пользователь → сайты → тема, черновик, публикации, события.
- **Правило именования** индексов и ограничений задано в `db.py`, чтобы будущие миграции могли надёжно их изменять.

### Схемы API

Схемы описывают формат данных в запросах и ответах (папка `backend/schemas`). Полное описание полей — на странице `/docs`, раздел Schemas.

| Схема | Что описывает |
| --- | --- |
| **Авторизация** (`auth.py`) | |
| `RegisterRequest` | Регистрация: название компании, e-mail, пароль, согласие с условиями |
| `LoginRequest` | Вход: e-mail и пароль |
| `UserResponse` | Данные пользователя в ответе (без пароля) |
| **Сайты** (`site.py`) | |
| `SiteCreate` | Добавление сайта: название и адрес |
| `SiteUpdate` | Изменение названия сайта |
| `SiteResponse` | Карточка сайта: адрес, статус виджета, число туров, запуски за 7 дней |
| `InstallationResponse` | Код подключения виджета (тег `<script>`) и статус подключения |
| `ObservedPage` | Страница, на которой работал виджет |
| **Настройка вида** (`theme.py`) | |
| `ThemeSchema` | Тема оформления: цвета, шрифт, скругление, положение, переключатели |
| **Конструктор** (`project.py`) | |
| `Project` | Весь проект сайта в формате панели (`schema: 4`) |
| `Scenario` | Сценарий (тур): название, цвет, способ запуска, шаги |
| `Trigger` | Способ запуска: приглашение, клик по элементу или вручную |
| `Step` | Шаг: заголовок, текст, страница, селектор элемента |
| `Variants`, `Variant` | Настройки шага отдельно для компьютера и телефона |
| `Action` | Действие подготовки перед шагом: клик или выбор в списке |
| `Page` | Страница сайта в списке конструктора |
| `ProjectSaveRequest` | Сохранение черновика: проект и номер исходной ревизии |
| `ProjectResponse` | Черновик в ответе: проект, ревизия, ревизия последней публикации |
| **Публикация** (`publication.py`) | |
| `PublishRequest` | Какую ревизию черновика опубликовать |
| `PublicationResponse` | Публикация: номер версии, исходная ревизия, дата |
| **Виджет** (`public.py`) | |
| `WidgetConfig` | Конфигурация для виджета: формат `exportProject` + версия и тема |
| `PublicScenario` | Сценарий в конфигурации (без служебных полей панели) |
| `ConnectRequest` | Сигнал подключения виджета: страница, версия виджета |
| `EventIn` | Одно событие прохождения тура |
| `EventBatch` | Пачка событий (от 1 до 50) |
| `EventBatchResponse` | Сколько событий принято и сколько оказалось повторами |
| **Аналитика** (`analytics.py`) | |
| `AnalyticsSummary` | Сводка: запуски, пропуски, завершения, таблица по турам |
| `ScenarioStats` | Статистика одного тура |
| `Timeseries`, `TimeseriesPoint` | Данные для графика по дням |
| `Funnel`, `FunnelStep` | Воронка по шагам одного тура одной версии |
| `AnalyticsFilters` | Фильтры аналитики из адреса: сайт, тур, период, устройство |
| **Общие** (`base.py`) | |
| `CamelModel` | Основа всех схем: поля в JSON в стиле camelCase |
| `ClientId`, `HexColor` | Типы: id от фронтенда (1–100 символов), цвет `#RRGGBB` |

`HTTPValidationError` и `ValidationError` на странице `/docs` — встроенные схемы FastAPI: формат ответа 422 при ошибках в данных.

### Безопасность

- **Вход по JWT в заголовке `Authorization`, а не через cookie.** Панель (GitHub Pages) и API находятся на разных сайтах: cookie стали бы сторонними, а Safari и Firefox их блокируют или изолируют. Переход на cookie (`HttpOnly`, `SameSite=Lax`, проверка заголовка `Origin`) имеет смысл, только если панель и API окажутся на одном сайте.
- **CSRF не страшен:** браузер не добавляет заголовок `Authorization` к запросам сам, а чужой сайт не знает токена.
- **Главный риск JWT — XSS** (выполнение чужого скрипта в панели и кража токена). Снижается так: Vue выводит данные как текст, виджет — через `textContent`, сообщения `postMessage` принимаются только от проверенных источников, токен действует сутки, есть «выход на всех устройствах».
- **Все проверки — на сервере.** Запрос к API можно отправить в обход панели (консоль браузера, Postman), поэтому формат данных проверяют схемы, вход — `get_current_user`, а права на сайт — проверка владельца.
- **Защита от доступа к чужим данным (IDOR):** сайт ищется по id и владельцу одновременно, чужой сайт неотличим от несуществующего.
